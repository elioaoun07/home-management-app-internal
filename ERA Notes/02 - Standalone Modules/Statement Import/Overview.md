# Statement Import

> **Type:** Standalone

## Key Concepts

- **The statement is an audit, not an entry path.** The owner logs card taps as they happen (Hub chat, voice, expense form); uploading the statement afterwards *reconciles* it against those logged transactions. Rows that match need no work — only the leftovers get categorized. This is the module's north star; every design decision below follows from it.
- **Posting lag is the matcher's job, not the user's.** Banks post a tap 1–3+ days after it happens, so matching uses a date window (logged date ∈ [posting − 7d, posting + 1d]) plus amount and merchant-text signals, never date equality.
- **Stamping is balance-neutral.** A matched row only writes `statement_hash` onto the existing transaction. Creating, confirming a draft, or accepting the bank's amount are the only paths that move money — see the invariants in `src/app/api/statement-import/commit/route.ts`.
- Review work is persisted to IndexedDB (`src/lib/statementImportSession.ts`) and resumable; nothing is lost by navigating away.
- **Every commit is a revertible batch.** A bulk write the user cannot walk back is the real hazard with statements, so the commit route opens a `statement_imports` record and writes one `statement_import_entries` row per transaction it touches — carrying both the state it found and the state it wrote — *before* any balance moves. If either cannot be written it returns 503 having changed nothing. `POST /api/statement-import/imports/[id]/revert` replays that ledger backwards: created rows are soft-deleted (Recycle Bin) with their hash freed so the statement stays re-importable, stamps are un-stamped, confirmed drafts go back to draft, merchant mappings are restored to their pre-import value, and balances move back. The rules live in `src/lib/statement-revert.ts` — deltas are always computed from **live** row state (so an amount edited after the import still nets to zero), and a newer human edit is never overwritten.
- **The statement account is part of the dedupe key.** Hash v2 is `v2|account|date|description|moneyOut|moneyIn`. The fingerprint always names the statement source, while the resulting transaction may deliberately land in another account (for example, a salary-statement bank fee mapped to Debit NEO / Bills). Exact hashes are searched across all owned accounts.
- **Imported means identity, Matched means evidence** (BUD-58). Existing → Imported contains exact `statement_hash` hits only, including a row previously routed to another account and a soft-deleted transaction whose occupied fingerprint must not be recreated. Existing → Matched contains fuzzy/legacy matches and already-recorded person transfers. Exact Imported rows never stage `Re-tag`/bank-text maintenance in Ready; only a fuzzy hit with a genuinely stale fingerprint can stage a balance-neutral re-key.
- **PDF parsing is coordinate-aware and fail-closed** (BUD-58). The default PDF text renderer can concatenate adjacent MONEY OUT / MONEY IN / BALANCE columns (`-2,534.002,534.00`), which silently removed every credit in the real corpus. `pdf-parser.ts` now rebuilds each visual line by Y coordinate and X order. Parse diagnostics count candidate/parsed/balance/rejected blocks; any rejected dated money block returns 422 before review rather than importing a partial statement. Integration tests parse the three real statement fixtures: Debit 390, Salary 154, Savings 32, with zero rejected rows.
- **Own-account moves are never money.** Rows whose description names an internal transfer or an own-account FX leg ("Own Account Exchange: USD to EUR at 0.852 - from 501400630004", "Transfer from Own Account …") classify as `transfer` and produce no commit action — money-rules Invariant 4. Until 2026-08-24 only `/transfer\s+(from|to)/` was recognised, so every FX leg imported as a real debit or credit; the two legs cancelled on the balance, which is why the damage showed up only as phantom income and phantom spend in analytics. The pattern list (`OWN_ACCOUNT_PATTERNS` in `src/lib/statement-reconcile.ts`) is deliberately conservative and anchored to an explicit "account"/"transfer" word — a false positive silently drops a *real* expense, which is the worse failure, so bare `/exchange/` is not enough ("Currency Exchange Hamra" is a merchant).
- **A statement amount has EXACTLY two decimals, and the parser's money regexes MUST carry `(?!\d)`** (BUD-55). Without it, `[\d,]+\.\d{2}` matches the first two decimals of a THREE-decimal number — and statements carry those: an FX rate. `Own Account Exchange: USD to EUR / at 0.852 - to 501400630005 - / 200.00 - 1,909.46` wraps across three extracted lines; the continuation line holds only the rate, so the row-assembly loop mistook it for the numbers line, broke out early, and read **`0.85` as MONEY OUT**. Every exchange imported as $0.85 with the rate stripped out of the description, which is why they all classified as plain own-account moves and sat on Skipped no matter what the downstream routing said. The three patterns are now named constants (`MONEY_ANYWHERE`, `TRAILING_AMOUNTS`, `MONEY_OR_DASH`) in `bank-statement-parser.ts`; any new amount pattern must carry the guard. Note the two used with `.test()`/`.search()` deliberately have **no `g` flag** — a global regex carries `lastIndex` between calls and would silently skip every other row.
- **A description can wrap around a DATELESS amounts line, not just before it** (BUD-59). The parser only ever starts a row from a line beginning with a date — but this bank sometimes prints the date next to the AMOUNTS instead of the first description line, when the description overflows onto an earlier physical line (even across a page break): `Transfer to JOHN GEORGES` / `YAZBECK via Mobile - malak el` / `18/06/2026 14.00 - 192.97` / `tawouk 2 burgers`. The two orphan lines before the dated amounts line had no date to anchor to and were silently dropped as noise between transactions, producing an EMPTY description (`"(no merchant)"`, `type: "unknown"`) instead of a person transfer. A `pendingOrphan` buffer holds any line that is neither dated nor carries money; the next dated line resolves it — amounts-only content means the buffer IS this row's description (prepend, recomputing `type`/`merchantName` from the corrected text), anything else means the buffer was the PREVIOUS row's trailing overflow (append to the already-pushed transaction). One mechanism recovers both the leading wrap (before a dateless amounts line) and the ordinary trailing wrap (after any row's amounts, `tawouk 2 burgers` in the example) — do not add a second, separate code path for either direction. **The bank's one-time authenticity footer must be filtered before this buffer sees it** — `For Verifications` / `Scan the QR code` / `This Tamperproof is digitally signed.` / … has no date and no money either, so it reads exactly like an orphan continuation and was found gluing itself onto whichever transaction happened to precede it in the real fixture corpus. `DOCUMENT_FOOTER_PATTERN` strips it before the main loop runs. Any new bank format added to this parser needs the same audit: does it ever print a row's date somewhere other than the first description line, and does it have page-level boilerplate with no date/money signature?
- **An own-account CURRENCY EXCHANGE is the one own-account move that is not noise** (BUD-54). `Own Account Exchange: USD to EUR at 0.852 - to 501400630005 -`, MONEY OUT 200.00, is the owner buying EUR with USD — the destination account gains **170.40 EUR**, a different number from the one on the statement, so skipping the row leaves that account permanently short. `classifyOwnExchange()` reads both currencies, the rate and the counterparty account digits off the line and stamps them as an `exchange` FLAG (like `withdrawal`), so an already-imported or hand-logged exchange still reports its real status. The row lands on the Transfers tab's **Exchange** section; picking the destination stages a SELF `create_transfer` carrying `to_amount` (the converted figure), and the commit route derives `transfers.exchange_rate` from `to_amount / amount` rather than trusting a client-sent rate — the same rule `POST /api/transfers` follows. `transfers.to_amount` / `exchange_rate` already existed, so **no migration**.
- **Only the OUT leg of an exchange is actionable.** The identical bank line appears on BOTH statements — money OUT 200.00 on the USD side, money IN 170.40 on the EUR side — and the two rows hash differently because the account is part of the fingerprint, so nothing would stop the second import from writing the same movement twice. `direction` comes from the statement's own MONEY OUT / MONEY IN column, never from the wording (the wording is identical on both sides). The in leg stays on Skipped, labelled **"Other side of an exchange"**. Same rule, same reason, as "only the SENDER records a household transfer".
- **An exchange line's `" - "` separates FIELDS, not a memo.** `extractStatementMemo()` takes everything after the first `" - "`, which on `… at 0.852 - to 501400630005 -` yields `"to 501400630005 -"` — that would have become the transfer's default description. The memo is suppressed when the `exchange` flag is set, so the raw bank line stands.
- **The quoted rate is applied only when the destination account is actually in the target currency.** 0.852 is EUR-per-USD; multiplying a USD wallet's balance by it would invent money out of nothing. A mismatched destination gets a plain 1:1 move and the card states which amount lands. The picker is deliberately NOT filtered to the target currency — a picker that silently hides accounts is how a row becomes un-answerable — but every own destination is labelled with its currency. Conversion is rounded to cents **once**, in `convertAtRate()` (money-rules Invariant 8: 200 × 0.852 is 170.40000000000003 in float, and that number would have been written to a real balance).
- **Imports are per-importer; the TARGET account may be the partner's public one** (BUD-81). The statement picker offers own accounts plus the partner's visible `is_public` accounts (same set as the expense form); parse/reconcile/commit/revert authorize through `listWritableAccounts()` in `src/lib/accountAccess.ts`. Everything else stays the importer's: rows are written with their `user_id`, the `(user_id, statement_hash)` fingerprint key is unchanged, and reconcile matches only against the importer's own transactions — the partner's rows on the same account are never candidates. Commit reads categories by id without `user_id` scoping (a shared account's categories belong to its owner) and pins each to the row's access-checked account.
- **Own-account transfers are skipped; person-to-person transfers are IMPORTED.** `isTransferDescription()` matches only own-account wording (`transfer from|to own`, `own account`, `account exchange`, `internal transfer`, `between my|own accounts`). `isPersonTransfer()` covers the rest of `transfer from|to` — "Transfer to RACHA SAMIR TOUMA via Mobile" is real spending and "Transfer from SALIM …" is real income. A blanket `/transfer (from|to)/` rule used to swallow both, so paying a friend never reached the ledger. Direction comes from the statement's own MONEY IN / MONEY OUT columns, never from the wording.
- **A row is auto-targeted at an account that can represent its direction** (`suggestAccountForRow`). An income/saving account can only ADD (`getBalanceDelta`), so a money-OUT row filed there moves the balance the WRONG WAY — a $400 ATM withdrawal on a Salary statement would *raise* Salary by $400. No encoding fixes that, so such rows default to an expense account (preferring `is_default`). Separately, money IN from another person on an expense account defaults to an income account — income, not a card refund. Both are only DEFAULTS: the per-row select still wins and shows the resolved account, and the merchant card appends the target name when it is not the statement's own, so a redirect is never silent.
- **The income-account default has its OWN flag, `accounts.is_default_income`, independent of `is_default`** (2026-08-26, `migrations/2026-08-26_accounts-default-income.sql`). `is_default` is a single app-wide flag shared with the everyday quick-entry default (`ExpenseForm`, `MobileExpenseForm`, HubPage, watch views, …) and in this household sits on an expense account (Wallet). `pickAccount(accounts, "income")` used to reuse that same flag for the income redirect above, found no income-type candidate carrying it, and fell through to `candidates[0]` — whichever income account happened to be first in the array (Drawer, a physical cash account also typed `income`), not the household's actual preferred landing account (Salary). This also explained a second-looking symptom: `categoryOf()` (see the BUD-53 entry two lines up) merges categories from `pickAccount(accounts, "income")`'s account, so with the wrong account resolved, a category the owner picked after manually overriding the row to Salary lived on an account `categoryOf` never fetched — the chip fell back to "Choose category" even though the pick was saved correctly. Both symptoms shared the one root cause; fixing `pickAccount` fixed both, no separate categoryOf change needed. Set via Settings → Accounts → "Set income default" (`PATCH /api/accounts/[id]/default-income`, `useSetDefaultIncomeAccount`), enforced to one true row per user by a partial unique index + trigger mirroring `ensure_single_default_account`.
- **A transfer between household members is a `transfers` record, never a transaction.** `matchHouseholdMember()` tests the statement line against the household's profile names; a hit classifies the row `household_transfer` and it never reaches the categorize flow. Living in a different table is what keeps it out of every spending aggregate *by construction* rather than by a flag someone can forget — which is the whole point: the sender's side has no category, and what the receiver later spends it on is a separate transaction with its own. Name matching requires EVERY significant word of the profile name to appear (banks pad with middle names: "RACHA SAMIR TOUMA" for a profile of "Racha Touma"), because a false positive would erase real spending from every total.
- **Only the SENDER records a household transfer.** `POST /api/transfers` requires the creator to own the from-account and the partner to own the to-account, so an incoming leg structurally cannot create a second copy of the same movement — it can only recognise the one the sender already made (`existing_transfer_id`, matched on amount + date window). That is what makes the two sides agree without a cross-user write. An unrecognised incoming leg waits in Skipped until the sender imports.
- **The exact-hash check runs before the transfer check**, so a row already written to the ledger reports "imported before" rather than hiding in the skipped bucket. That is what makes pre-fix phantom transfer transactions discoverable on a re-import.
- **Renaming preserves the dedupe key.** `RowDecision.description` changes only what is stored on the transaction; the fingerprint is computed once at parse time from the bank's raw text and never recomputed. So "PrePaid" → "ALFA Prepaid Phone" is safe: next month's statement still matches on the bank's wording.
- **One statement → one account, with a per-row escape hatch.** The account is chosen deliberately before upload (no default — it used to pre-select `is_default`, which meant the target of a bulk money write could be chosen by not noticing it) and is shown in the review header for the whole session. `RowDecision.account_id` re-targets individual rows for the real exception: bank fees riding along on a salary statement are a charge against the expenses account, not salary income. Overriding clears the row's category, since categories are account-scoped.
- **The fingerprint is keyed to the statement's account, never the row's destination.** That is what makes the override safe: a re-targeted row keeps the hash of the statement it came from, so next month's import still recognises it. The consequence is that **reconciliation looks hashes up across every account**, not just the statement's.
- **`other_account` — same money, different account.** A row whose exact date, amount and direction match a transaction in a *different* account is flagged, never auto-skipped: it is either a deliberate past override or a mis-filing worth moving, and only the owner can tell. Description is deliberately **not** a gate (a mis-filed transaction is usually hand-typed, so its wording is the owner's, not the bank's) — it ranks which twin to show, and both descriptions go on screen.
- **A fingerprint-formula change repairs itself on the next import.** When the fuzzy duplicate tier recognises a row whose stored hash differs from the current formula's, the commit step **re-keys** it (`rekey` action): `statement_hash` only, balance-neutral, guarded on the previous value, written to the revert ledger like any other change. The v1->v2 change (2026-08-19) shipped without a backfill and left 152 rows matchable only by resemblance; re-importing now upgrades them to identity matching. Re-key never fires for an exact-hash hit (nothing to upgrade) and a 23505 collision means the row is a genuine duplicate rather than an outdated key, so it is left alone.
- **Transfers carry the fingerprint too** (BUD-56, 2026-08-25). `transfers.statement_hash` + a unique index on `(user_id, statement_hash) WHERE statement_hash IS NOT NULL AND deleted_at IS NULL`, mirroring `transactions_statement_hash_uniq`. Until this, transfers were the ONE thing this feature writes outside `transactions` and the only one with no identity: the hash was recorded solely in the `statement_import_entries` ledger, which the reconciler never reads, so on a re-import every household transfer, cash-withdrawal-to-wallet and own-account exchange came back as brand new — one confirm away from moving **both** balances a second time, with nothing anywhere to flag it. The reconciler now looks live transfers up by fingerprint (`ImportedTransferRef`) in the same pass as transactions and returns `{status:"already_imported", reason:"transfer_hash", transfer_id}`; the commit route maps a 23505 on the insert to `skipped_duplicate`. The transfer arm has **no fuzzy tier and no re-key/backfill path** — a transfer has no `bank_description` and nothing to upgrade — so `buildCommitActions` bails on it before every other branch, which also matters because the `withdrawal` / `exchange` flags survive onto an already-imported row (pass 5 stamps every row) and a stale destination pick would otherwise be enough to write the movement twice. The index excludes soft-deleted rows on purpose: a transfer can be removed by reverting its import **or** from the Transfers module, and both must leave the statement row importable again — `transactions` reaches the same end differently, by nulling `statement_hash` on revert. Migration `2026-08-25_transfer-statement-hash.sql` backfills history from the ledger (`DISTINCT ON` per fingerprint, so pre-existing duplicates do not block the index) and ships the query that lists them for manual cleanup.
- **`bank_description` is the reporting axis; `description` is the human one.** The statement line is stored verbatim in `transactions.bank_description` on create, stamp AND rekey — so re-importing history backfills it for rows logged by hand. It is always the RAW row, never the rename, because the rename is the part that drifts ("Spinneys" one month, "Supermarket Spinneys" the next) while the bank's text is machine-generated and stable. It **cannot** be recovered from `statement_hash`: SHA-256 is one-way over free text, so there is nothing to reverse — storing it is the only option. Revert restores the prior value, and only when the import actually wrote one.
- **A skip is a decision about a bank ROW, not about one upload.** Manual skips are recorded in `statement_skipped_rows` against the row's fingerprint, so re-uploading the same period (or a wider range, or a freshly downloaded PDF) does not ask again — they come back as `skipped_before`. Transfers are deliberately NOT recorded: the matcher re-derives those on every run, so remembering them would fill the table with rows needing no memory. Restoring from the Skipped tab emits `unskip` and deletes the record. Kept out of `statement_import_entries` on purpose — reverting an import must not silently un-skip rows the owner ruled on separately.
- Merchant mappings are learned from rows the user categorizes, keyed on the normalized merchant string. A rename is **not** learned — it stays a per-row manual act by design. Neither is an account override: auto-applying a learned account is the BUD-23 bug shape.
- `merchant_mappings` is also read by Transactions' manual-entry auto-suggest via a shared hook (`src/hooks/useMerchantMappings.ts`) — see [Feature Map/standalone/statement-import.md](<../../01 - Architecture/Feature Map/standalone/statement-import.md>).
- **`skipped_before`, `memo` and `withdrawal` are FLAGS on `RowClassification`, never statuses** (BUD-51, `statement-reconcile.ts`). `RowClassification = RowStatus & { skipped_before?, memo?, withdrawal? }` — a row's real classification (`matched`, `person_transfer`, `unmatched`, …) is computed first, then the matcher's final pass stamps these on top. This is what lets Restore work: `getBucket` falls through to the row's real status once `skipped_before` clears, routing it to whichever tab it actually belongs on. Before this, `skipped_before` WAS the status and replaced the row's classification outright, so a restored row had nowhere to go and stayed stuck on the Skipped tab. `RowStatus` keeps the legacy `{status:"skipped_before"}` shape so a session already in IndexedDB (up to `MAX_SESSIONS`=3) still resolves without a migration.
- **Cash withdrawals** (`classifyWithdrawal()`) are ATM or voucher, told apart by the word "voucher" in the bank line. Parser type `cash_withdrawal` (`bank-statement-parser.ts`). `extractStatementMemo()` pulls everything after the FIRST " - " in the raw line — the owner's own note ("… for Voucher No 123 - Car Insurance" → "Car Insurance", "Transfer to X via Mobile - 'link bowling - for 2'" → "link bowling - for 2") — used as the default transaction description (`defaultDescriptionFor()`) and, for a withdrawal, the merchant name. Never touches `statement_hash`.
- **`Bucket` still has five model values**, but the page groups them by user job: Review → Transactions / Transfers; Existing → Imported / Matched; then Skipped and Ready. The model partition remains exact while the navigation no longer presents Transfers as unrelated to review or Logged as an unexplained synonym for Imported (BUD-58).
- **The Transfers tab has three sections**: People, Cash and Exchange (BUD-54), sub-nav shown only when more than one is non-empty, auto-falling back to a section that has rows. An **Exchange** row has NO `Transfer | Spent` toggle — an exchange is a move by definition, so offering "Spent" would only invite a wrong answer — and shows the bank's own arithmetic as one data line (`200.00 USD → 170.40 EUR @ 0.852`). Historically two sections: People and Cash, sub-nav shown only when both are non-empty. Both render through the SAME `TransferRowCard` (BUD-52) — a person transfer and a cash withdrawal ask the identical question, so they share one component and one `Transfer | Spent` toggle. People rows show sent (muted, ↑) vs received (emerald, ↓ with a `+`) and the counterparty; Cash rows show the withdrawal kind. On **Transfer**, the destination `Select` offers partner accounts (household `transfers` row) for a person row and the owner's own accounts (self `transfers` row) for cash, with `<statement account> → <destination>` shown explicitly. On **Spent**, an editable description defaulting to the memo plus a `CategoryChip` scoped to `resolveRowAccount()` (income account for a received leg, the statement's own otherwise — `suggestAccountForRow` routes this); `learn_mapping` is suppressed for withdrawals since their `normalized_key` is a reference number, not a merchant. `CategoryPicker`-in-a-bare-Drawer is factored into `CategoryPickerSheet`; the compact chip is `CategoryChip`.
- **One question decides every Transfers-tab row: `Transfer` or `Spent`** (BUD-52). Both a person transfer and a cash withdrawal ask the same thing — did the money move somewhere else, or is it gone? Only the destination differs (partner account → household `transfers` row; the owner's own account → self `transfers` row), so both render through ONE `TransferRowCard`. The old wording ("To wallet", "Partner / Not partner") never said from where, to where, or why it was not just spending; the card now shows `<statement account> → <destination>` explicitly. `treat_as_transfer` is the single stored flag behind the toggle.
- **The Transfer/Spent question is ONE `TransferToggle` component (`src/components/statement-import/TransferToggle.tsx`), used by both the Transfers-tab card AND the shared row editor** (2026-08-26). It replaced two separate `["Transaction","Transfer"]` button pairs — the one on `TransferRowCard` and the one inside `GroupSheet`'s `RowControls` — with one `role="switch"` control (a hand-drawn `TransferIcon` from `FuturisticIcons.tsx`, matching the app's own icon set rather than a generic lucide glyph) so flipping "did this move, or did I spend it?" looks and behaves identically everywhere it appears. **No filled knob** — an iOS-style white circle read as a bare default switch and clashed with the app's dark neon cards, so the icon sits directly on the pill track and slides position: `tc.textMuted` (a muted tint of the theme's own accent colour — cyan-400/70 by default) at rest, `text-white` + `tc.iconGlow` (the same neon drop-shadow every category icon gets) once lit. A decided `TransferRowCard` row collapses to a read-only summary — `<from> → <to>` pills for a picked destination, or a `CategoryChip interactive={false}` + the saved description for a picked category — and re-opens its control on tap; `CategoryChip` gained `interactive?: boolean` for this (renders a `<div>` instead of a `<button>` so it can sit inside the card's own edit-tap button without an invalid nested `<button>`).
- **Tapping a category/subcategory on the Transfers tab opens the SAME editor a Categorize-tab merchant does** (2026-08-26) — `TransferRowCard`'s "Spent" side mounts `GroupSheet` itself, as a synthetic one-row group (`rows={[row]}`), instead of the bare `CategoryPickerSheet`. `GroupSheet`'s `RowControls` already had the description input, the date field and a per-row account override; only the transfer-destination list needed scoping to this row's kind, so `GroupSheet` gained an optional `transferDestinations` prop that overrides `RowControls`' default "every other account" list — the Transfers tab passes its own kind-scoped `destinations` (partner accounts for a person row, the owner's own for cash), the ordinary Categorize flow passes nothing and keeps the old behaviour. `onGroupCategoryChange` for this synthetic group is wired straight to `onRowChange(row.id, next)` — a one-row group's "group category" and "row category" are the same target, so no `session.group_categories` entry exists or is needed for it. **The trap this uncovered:** the sheet used to mount only while `mode === "spent"`; once the shared toggle could flip a row to `"transfer"` from *inside* that same sheet, the mode change would unmount the sheet the owner was still editing. Fixed by gating the mount on `mode === "spent" || pickerOpen`, not `mode` alone — any future per-row editor that both reads AND writes the field controlling its own mount condition needs the same guard.
- **`GroupSheet`'s multi-row "N rows" disclosure defaults OPEN on every mount, not just when `focusRowId` points into it** (2026-08-26). The owner opens the sheet FOR the per-row detail on a multi-row merchant; making them tap twice to see what they came for was the bug, not a feature.
- **Every date on the review screen carries a year suffix ONLY when the statement spans more than one calendar year** (2026-08-26, `hasMultipleYears()` in `sessionModel.ts`, checked once per session and threaded down as `showYear` to every row-level component: `TransferRowCard`, `MatchedRowCard`, `GroupSheet`, `OtherAccountSheet`, `ReviewStepper`, plus the merchant-group and day-group labels in `page.tsx`). A single-year statement keeps the terser "21 Oct"; a statement crossing a year boundary (a Dec→Jan cycle, or a wide multi-month re-upload) shows "21 Oct 2025" everywhere instead of two indistinguishable "21 Oct" rows a year apart. `formatStatementDate(iso, { year?, weekday? })` in `sessionModel.ts` is now the one date formatter for the screen — six components used to carry their own copy-pasted `toLocaleDateString` call; do not reintroduce a seventh.
- **Durable state never lives in `RowDecision.resolution`** (BUD-53). `resolution` is overwritten by every subsequent decision, so encoding Restore as `resolution:"undecided"` meant the owner's next act — picking a category, picking a transfer destination — set it to `"create"`, `getBucket()` re-applied the row's `skipped_before` flag, and **the row vanished from the tab it was answered on, at the moment it was answered**. Restore is now `RowDecision.restored`, read through `isRestored()` (which still honours the legacy `undecided` encoding so an IndexedDB session resumes intact) and cleared by `updateDecision` on an explicit skip. Any future "this row has been promoted out of its default state" fact must be its own flag for the same reason.
- **Category names must resolve across every account the screen can target** (BUD-53). Categories are account-scoped and `suggestAccountForRow()` deliberately redirects rows off the statement's account, so a category map built from the statement account alone cannot name a category picked in a redirected row's grid — the chip fell back to "Choose category" and the owner's pick read as thrown away. `page.tsx` merges the statement, income and expense account category lists into one `categoryOf()`. Relatedly, a row's picker is opened on `resolveRowAccount()` — the account the row will actually be CREATED in — or the commit route rejects the pair as a category↔account mismatch.
- **The Skipped tab is three populations, not one list** (BUD-53). `skipReason()` splits it: **This import** (set aside during this review — the only ones still in play), **Previously skipped** (a standing skip recorded by fingerprint on an earlier import; re-deciding these monthly is the exact work the standing skip exists to avoid), **Own moves** (own-account transfers the matcher re-derives every run — no Restore, because there is nothing to undo). Each row states WHY it is there, read off the real classification under the skip (`Also in Debit Card - NEO`, `Transfer · SALIM`, `Cash withdrawal`, `Already imported`, …). This replaced a flat list plus a Show/Hide-own-transfers toggle, in which a 3-row decision sat inside 85 rows of remembered noise with no reason shown for any of them.
- **Deciding a row stages it; it does not file it away.** A decided row keeps its place in its tab and grows a green `✓ <verb> · <detail>` line stating exactly what Save will do. Nothing is written until Save — the owner asked for this specifically after selections felt like commitments.
- **The `Ready` tab is a CROSS-CUTTING view, not a sixth bucket — and it is the FINAL stage, so it sits last in the tab bar.** It renders `buildCommitActions()` — the same function the commit uses — through `describeCommitAction()`, so it can never promise something the commit will not do. A staged row appears both in its own bucket tab and here. Its count is `saveCount`, the number on the Save button. It opens with the **net ledger effect as one signed number** (`stagedNetAmount()` — credits add, debits subtract; transfers excluded because they net to zero across the owner's own accounts) and splits the list into three lanes via `actionLane()` (BUD-53): **Money** (`create`, `create_transfer`, `confirm_draft` — the balance moves; a draft was never counted in the stored balance, so confirming applies the delta once), **Matches** (`stamp` — an existing transaction gets the bank fingerprint), **Memory** (`rekey`, `skip`, `unskip` — nothing but what the next import remembers). Flat, the tab put a `Log` beside a `Restore` with nothing to say one moves money and the other writes none.
- **Verbs are the owner's words, not action kinds**: `Log`, `Move` (self transfer), `Send` (household transfer), `Match`, `Confirm`, `Re-tag`, `Skip`, `Restore`. `confirm_draft` and `rekey` mean nothing on screen.
- **Partner accounts come from `useHouseholdAccounts()`, never `useAccounts()`** (BUD-52 bug). `useAccounts()` exposes only the partner's `is_public` accounts, so a partner who keeps them private produced an EMPTY destination dropdown with no error anywhere — it looked like RLS and was not. A household transfer is exactly the case allowed to name a private partner account (BUD-13); `TransferDialog` is the working precedent and sources it the same way. The partner is identified explicitly via `useHouseholdPartner()` rather than by subtracting the owner's account list, so an account merely missing from `useMyAccounts` (hidden, say) can never be mistaken for the partner's.
- **Both household members use the SAME account names** ("Debit Card - NEO", "Salary", "Wallet" exist on both sides), so every partner-account label carries the partner's name (`Whish · Racha Touma`). A bare name in that picker reads as the owner's own.
- **`useHouseholdPartner()` (`src/hooks/useHouseholdPartner.ts`) resolves the display name via `/api/household`**, which reads `auth.users` metadata server-side through `supabaseAdmin()`. `useHouseholdMembers()` reads the `profiles` mirror from the browser, and that table can be empty (BUD-47) — which degrades every name to an email prefix (`rachatouma`). Kept as a separate hook so the four features already depending on `useHouseholdMembers`'s exact shape are unaffected.
- **The tab bar scrolls, it does not truncate.** The count IS the information ("Skipped 85"), and equal `flex-1` slots with `truncate` cut exactly that off. `ScrollableTabs` gives each tab its natural width and fades the edges with a **CSS mask** rather than a gradient overlay — `tc.pillBg` is a translucent per-theme colour, so an overlay would have to know what is behind it in all four themes. The fade appears only on a side that can actually be scrolled toward; `scrollEdges()`/`edgeMask()` are pure and unit-tested (`ScrollableTabs.test.ts`). The scroll listener is attached **natively** with `{ passive: true }`, not via React's `onScroll` — `scroll` does not bubble, and passive keeps touch-dragging smooth on a phone.
- **Self transfers** (`transfers.transfer_type = 'self'`) are the ATM-withdrawal-to-wallet case — no `recipient_user_id`, no `household_link_id`, same `getTransferDeltas()` math as a household transfer with `returnedAmount` always 0. `transfers.transfer_type` already allowed `'self'` in the schema before this shipped (Transfers module), so BUD-51 needed no migration; `statement-revert.ts`'s `create_transfer` reversal reads `applied.amount`/`to_account_id`/`to_delta` generically off the ledger entry and needed no change either.
