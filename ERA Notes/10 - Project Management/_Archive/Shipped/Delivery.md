### DLV-108

- ✅ 2026-09-20 — **DLV-108** Terminal-job recovery. `dispatch_started_at` only ever closed the window *before* a provider call; everything a finished job owes — plan, candidate, evidence, result, PM writeback — is written after settlement and outside that transaction, and a job in that window is terminal, so `listOutstandingJobs` (reserved/active/paused/unknown) could not see it and `reconcile()` left it untouched forever. Store schema 8 adds `jobs.settled_at`, stamped inside the same UPDATE that makes a job terminal — in `updateJob`, so every path that settles a job (normal dispatch, reconciliation from a retained container log, an observed stop) marks it — and `jobs.after_state` (`done` / `deferred` / NULL). `listSettledUnprocessedJobs()` is the counterpart scan, and `reconcile()` drives `afterJob` over it. `afterJob` now **resumes** rather than restarts: its old guards ("a plan already exists for this job → return") were written for re-entrancy inside one process and were exactly wrong across a crash, where a recorded plan with the run never moved to review, or a frozen candidate with no result, is the normal interrupted shape. A candidate with no result is re-checked from its own frozen bytes; a candidate a result already names has its run transition and writeback re-applied from the stored record instead of minting `result_version` 2. Recovery never dispatches — `allowRepair: false` on that path on purpose, because a repair is a new provider dispatch and recovery may not spend tokens the owner did not watch it decide to spend. A job settled under a position that declines the follow-on (paused, stop-requested, queued, scope-conflict) is `deferred`, not done, and reopened when that position clears. Related cleanup ordering fixed in the same pass: reconciliation used to `runtime.release` — which removes the container, and the container log *is* the replay material — before `recordDispatchResult` committed, so a failed recovery write was permanent; release now happens only after the store accepts the outcome. Rows written before schema 8 carry `settled_at IS NULL` and are deliberately never scanned, so an old closed run cannot be re-driven into a second result. Evidence: `scripts/delivery-v2/store.mjs`, `journey.mjs`; tests `tests/delivery-v2/journey.test.ts` — 14 new cases (7 boundaries × Claude/Codex, plus the legacy-row guard), each dropping the process at one durable boundary, reopening the store and reconciling **twice**, asserting exactly-once completion (one plan/candidate/result at version 1), no redispatch (`h.calls` flat), no doubled usage (banked input/output/cost identical) and recoverable artifacts (candidate bytes, evidence, writeback). All 14 verified to fail against the unfixed source. Full suite 2,906 passed; typecheck and ESLint clean. Local Delivery SQLite only — no Supabase migration. Owner restart-recovery UAT (U18) remains Pending: these are deterministic fixtures with scripted SDKs, not a real crashed provider run.
