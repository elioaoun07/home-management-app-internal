## Things an automatic view would have flagged

Each is a real state of the repository at the cutoff, and each becomes a test case for the [conflict detector](<05 - Conflict and Drift Detector.md>).

1. `.codex/hooks.json` calls its scripts by an absolute Windows path under one user's profile, so it can only work on that machine and that folder name. `.codex/settings.json` wires a different, single hook. Nothing in the repo shows which file Codex reads, or that either fires.
2. `.agents/skills/cache-invalidation/SKILL.md` lacks the "Other cache layers" section the Claude copy has.
3. `.claude/hooks/sync-copilot.sh` is dead: the wiring calls the Node script directly.
4. `.husky/pre-commit` is not executable, so the documented pre-commit gate does not run on Linux.
5. The deny list names `mcp__claude_ai_Supabase__*`; a cloud session exposes `mcp__Supabase__*` ([R84](<../../PM Tooling/PM Tooling — Master Book.md#r84>)).
6. `ERA Notes/CODEX.md` is a July security checklist that shares its filename with the generated root mirror.
7. `finish-task` names six campaign folders for the PM trace; there are eleven.
8. `start-task` lists nine junction modules, `CLAUDE.md`'s junction table lists ten, and they differ: Trips and Meal Planning are each a junction in one place and not in another.
9. Delivery V2 launches its workers with `"skills": []` and `"settingSources": []`, so the delivering agent has none of the above.

## What could not be seen

User-level settings: the Model Registry says efforts and defaults live in `~/.claude/settings.json` and `~/.codex/config.toml`. PM.2 should read those read-only and show the effective configuration by precedence (user, project, local), because that is what a session really runs with.
