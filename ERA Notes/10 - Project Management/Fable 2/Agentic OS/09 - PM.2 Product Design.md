# Agentic OS — PM.2 product design

[Agentic OS index](<_index.md>) · [Skill launchpad](<08 - Skill Launchpad.md>) · next: [Visual, motion and game layer](<10 - Visual, Motion and Game Layer.md>) · item: [R97](<../../_Archive/Shipped/PM Tooling.md#r97>)

## Two products, one server

**Usability correction — 2026-11-14 (R101, owner-requested):** the five destinations and evidence model stand. The original specification described content and signature visuals, but left hierarchy, control sizing and disclosure unspecified. The first implementation rendered the inventory literally: long forms, tiny verdict targets, a full graph on entry and JSON as the flight report. Passing overflow checks did not establish usability.

The revised presentation contract is:

1. **Bridge:** one visible New task action; Needs you / Running / Next up queues. R102 replaces the supporting metric row with passive SDK status and an optional chart-led Game view. Work titles wrap rather than truncate. Session uncertainty remains explicit.
2. **Launch:** choose a skill card or recipe, configure a compact labelled form, then Review prompt. The prepared result receives focus; copy controls require current validated inputs. Native worktree launch is not offered while unsupported. Empty derived titles stay empty.
3. **Sessions:** searchable cards with outcome and date, expandable numbered rule targets of at least 40 px, readable timeline facts and six summary panels. Raw JSON is a secondary disclosure. Pinning, same-item links and file/line findings remain accessible.
4. **Setup:** Overview opens agent selectors and a searchable category browser. The six-column connection map remains available in a disclosure, scrolling within its own container. Rulebook is searchable; conflicts collapse by class with counts and source evidence inside.
5. **Score:** consistent Sessions / Backlog / Arena navigation, prominent measured totals, recent session rows and cohort dimensions behind a disclosure. Unknown evidence never becomes a success or invented rate.

Desktop and phone use equal-weight primary destinations with a visible active state. Blue/Pink tokens and reduced motion remain shared. Visual QA must exercise expanded disclosures and complete workflows, not only initial screenshots. Browser evidence is local fixture evidence, not deployment or owner aesthetic acceptance.

**Implementation delta — 2026-11-14 (R97):** the existing React shell now hosts the cockpit and Library destinations. The owner explicitly included Library parity plus test-gated retirement of the two local rollback UIs, and full read-only phone Sessions through the current relay. Launch reuses Delivery; skill forms/recipes remain A6. Historical file hashes and whole-tree baseline time series were never recorded by A1–A4: comparison shows the recorded fingerprint/count differences, and the Rulebook trend shows recorded session violation deltas alongside the recorded baseline. Missing facts remain unknown. See [implementation evidence](<../../../../docs/Skills-and-Agents.md#pm2-cockpit-a5--r97>).

| | PM.1 — Library | PM.2 — Cockpit |
|---|---|---|
| Is for | Reading and editing what is written | Seeing what is happening and starting things |
| Holds | Documents, checklists, Master Books, decisions, inbox, shipped history, plans, Fable 2 | Today, launches, sessions, setup, rules, scores |
| Source | Markdown files | The registry, the flight recorder, git, the same checklists (read-only) |
| Changes files | Yes: tick, move, capture, rename | Only through an explicit action that PM.1 could also do (Ship, capture) |
| Feel | Calm, text-first | Live, visual, animated |

Both are served by `pnpm pm`. PM.2 is the default screen once it is ready; PM.1 is one click away as **Library**. Until then PM.2 lives at its own path and PM.1 is unchanged.

## Screens

### Bridge

One question: what now?

**Owner-approved revision — 2026-11-14 (R102):** Game layer off is the calm daily-action view. Game layer on presents the same queues around an ERA core, with evidence-backed charts. Both retain New task, the same item/session links and an immediately reachable Game layer switch. The preference is shared with Settings and persisted per browser.

```text
 Bridge                              Game layer [Off / On]       New task

 Needs you                    Running                    Next up
 [decisions and reviews]       [observed active work]      [ready work]

 Game on: ERA state core · eight-week outcomes chart · session quality chart

 Claude SDK [observed status]           Codex SDK [observed status]
```

- **Calm view:** the three action queues and compact SDK footer. The former Bridge guard/conflict tiles move to Setup; clean streak remains in Score. Setup gets a numberless attention indicator for actionable conflicts or missing intended guards, not every rule that deliberately needs human judgment. Existing Score evidence mirrors remain; redesigning Score awaits its separate owner review.
- **Game view:** the ERA core continuously rotates while visible, with observed running work taking precedence over owner-waiting counts. Running uses red/orange friction, smoke and embers; waiting for approval/action uses gentler yellow motion; explicit success uses green; failed completion uses a grey broken offset ring. Unknown/stale evidence never implies a terminal success, and partial/cancelled outcomes do not earn green. Activating the core by click or keyboard creates a bounded throttle burst without opening Sessions or dispatching a command; Open sessions remains a separate link. Reduced motion stops rotation and particles, and hidden/offscreen animation pauses. The outcomes chart uses the existing canonical shipped-outcome series over eight weeks, with unrecorded dates separated. The session-quality chart uses non-Arena records and the existing clean/failed/unknown evidence contract; incomplete checks or rule coverage cannot count as clean. Each chart retains source links or disclosure; no synthetic session activity or invented success rate.
- **Footer:** Claude/Codex dots report observed SDK installation. Installed does not establish authentication, subscription quota or provider uptime. Unknown and stale status remain distinct. The relay catalogue has no measurement timestamp, so a phone's known installation value remains Stale and an absent or unmeasured entry Unknown; fetching a saved catalogue cannot make it fresh.
- **Responsive behavior:** laptop uses the core, charts and queues as one canvas. Phone uses a compact core and stacked queues, with charts below and no page-level horizontal scrolling. Needs you remains directly accessible.
- **Transition:** explicit mode switches play the approved 1.8 s enter / 1.0 s exit sequence; reload does not replay it. Controls remain usable, rapid toggles settle on the selected mode, and reduced motion disables the choreography. The [motion amendment](<10 - Visual, Motion and Game Layer.md#motion>) records the mode-transition exception and the owner's later sustained Game-core exception; the 400 ms/no-loop ceiling continues to govern ordinary calm-mode feedback.

Primary actions remain New task and Deliver on a Next-up row. Outcome charts describe recorded completion, not owner UAT acceptance or deployment.

**R104 session scope:** the core's yellow state counts delivery approvals/actions. Standing PM/backlog decisions stay in Needs you and do not override the latest session's success or failure color.

**R105 overload refinement:** click/keyboard throttle and observed running use a fast friction wheel with red/orange heat, outward sparks/flame trails, smoke and local vibration. The simulated throttle leaves the real caption unchanged. Acceleration, repeated activation and gradual cooldown preserve angular continuity; cooling effects fade instead of stopping abruptly. Reduced-motion, hidden/offscreen pause and separate navigation contracts remain.

**R106 appearance refinement:** ERA's mark and thin orbital arcs replace the tire-like spokes/tread/track. An elliptical counter-orbit and distributed energy trails keep the core abstract. Sparks, smoke, glow and vibration are softened while acceleration and natural cooldown retain R105's behavior.

### Launch

The [skill launchpad](<08 - Skill Launchpad.md>): skill cards, recipes, a form, a rendered prompt, tier and location, one Launch button. Starting from an item pre-fills the `item` field and suggests the skill by the item's kind (bug → `fix-bug`, ERA report → `era-wire`).

### Sessions

A list, newest first: agent, tier, item, duration, verdict strip (green, red, grey ticks for the 29 rules), outcome. Opening one shows the [flight report](<06 - Flight Recorder.md>) as a horizontal timeline:

```text
prompt ─ skills ─ reading ─ edits ─────────── hooks ─ checks ─ verdicts ─ UAT ─ ship
  ●        ●●        ●●●     ●●●●●●●●●●        ✓✓✗✓     ✓✓✓      27✓ 1✗    ◌      ◌
```

Clicking a red mark opens the file and line. A session with an item shows the item's other sessions beside it, which is the delivery view. Two sessions can be pinned for comparison with their setup diff between them.

### Setup

Three tabs.

**Map.** Columns left to right: Agents · Instructions · Skills · Hooks and permissions · Checks and detectors · Rules. Lines connect what enforces or mirrors what. Selecting an agent greys everything it does not have, which makes the gap between Claude and Codex the first thing seen. Selecting a rule lights its whole chain or shows that it has none.

**Rulebook.** The 29 rules as cards: number, short title, shield level, baseline count with a trend line, last session that failed it. Sort by "weakest first".

**Conflicts.** The rows from `os:check`, grouped by class, each with the two sources side by side and "Open as item".

A small **fingerprint glyph**, generated from the setup hash, sits in the header. When the setup changes the glyph changes, so a glance tells whether two sessions ran under the same rules.

### Score

Panels: clean rate over time; rule failures by rule; process completeness; tokens per shipped item by tier; added against shipped per week; escapes. Tier cards summarise each alias with its real numbers and sample size. The Arena, when it exists, is a tab here.

### Plan

Today's Sprints view with elapsed weeks closed.

## Empty and early states

PM.2 is useful before any session is recorded: Setup works from the registry alone on day one. Sessions and Score show what they need ("no sessions recorded yet · wire the recorder") and never fake a chart. The first ten sessions show as rows, not rates.

## Phone

Bridge, Sessions (read-only) and UAT work on the phone. Launch and Setup are desktop screens first: a form with pickers and a six-column map do not fit 390 px, and starting agents from the phone is out of scope ([vision](<01 - Vision and Hype Filter.md>)).

## Rules the design holds itself to

- Hard Rule 28: labels, numbers and one- or two-word buttons. Help sits behind an `i`.
- Every number opens its evidence in at most one click.
- No screen exists in both products.
- No state lives only in PM.2. Clearing `.os/` loses history, never backlog or rules.
- Colour carries state consistently: the same green, amber and red as verdicts everywhere; person colours stay person-absolute where a person appears (Hard Rule 14).
