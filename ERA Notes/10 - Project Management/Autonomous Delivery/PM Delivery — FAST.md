# PM Delivery — FAST

## 1. Minimum trustworthy loop

**Bind intent → edit an isolated candidate → check the requested proposition → deliver the candidate and its evidence.** Everything else earns its place by resolving a real risk.

FAST is suitable when intent is clear, the relevant implementation pattern is known, the impact is bounded and an appropriate observation can establish success. File count and cheap model selection alone do not establish low risk. A one-line balance change can be high consequence; a larger mechanical edit can be straightforward.

V2 folds INSTANT into FAST as an exact-transformation strategy. STANDARD becomes ordinary engineering effort inside FAST or DEEP DIVE. It keeps two owner-facing choices. This is proposed V2 behavior; V1 retains its four lanes and recorded approvals until a separately authorized cutover.

## 2. Before dispatch

The kernel resolves stable work identity and source revision; it never starts from a bare checkbox ordinal. It constructs a compact contract from the request, relevant source and a tested task template where available. Required facts are outcome, exclusions, allowed write scope, acceptance propositions, evidence methods, resource allowance and integration policy.

Straightforward work can use a previously authorized policy preset. The owner sees the concrete task at launch and can edit its scope. There is no mandatory model-written specification followed by a separate model-written plan. When intent is unresolved, clarify before edits; a reasonable implementation choice within scope does not require another gate.

Baseline checks are reused only when their complete source/environment fingerprint matches. Changed dependencies, test configuration or relevant untracked inputs invalidate them. An existing unrelated failure is recorded as baseline evidence; it cannot be waived for a criterion that depends on the failing check.

## 3. Execution and checking

One engineering conversation receives the contract, focused context and bounded tools. It can inspect more source when a concrete dependency justifies it. Mandatory repository/domain invariants remain available and cannot be dropped to fit a token budget. The engineer proposes edits only to the candidate.

The checker freezes the candidate, checks unauthorized changes, and runs the required observation. A literal replacement can use an exact transformation witness. A behavior change needs behavioral evidence. No model review or UAT-generation turn is necessary for a mechanically established, low-risk proposition. A missing observation cannot be replaced by a stronger model's opinion.

Allow a small explicit repair allowance, initially one failed-check repair attempt for pilot work. The limit is a policy parameter, not a universal optimum. Each attempt has a new ID and its own usage receipt. Never silently widen scope to make a test pass. A failure outside the allowance returns a useful candidate plus the unresolved obligation.

## 4. Complete journey: quick-amount preset

This hypothetical V2 replay uses the historically expensive BUD-14 request; it is not a run performed by this study.

| Moment | Owner | System / engineer | Evidence and failure handling |
|---|---|---|---|
| Capture | “Replace the mobile $25 quick amount with $20” | Resolve current work and source; check the actual file and caller | Historical file pointers are hints, not current facts |
| Contract | Starts FAST with a bounded preset | Record displayed preset and intended action-value binding | Exact diff plus a qualified mapping witness or mounted/browser interaction; do not infer a working control from edited text alone |
| Execute | Can leave | One engineer changes the isolated candidate | Broker records before/after hashes, denies unrelated writes |
| Check | No action | Assert exact intended transformation and no extras; run applicable compile/behavior checks | Zero selected tests means no behavioral evidence. Do not run a vacuous test merely to show green |
| Failure branch | Only asked if an actual scope choice is needed | If preset is generated or shared with another surface, investigate dependency | Update contract/grant when meaning or authorized scope changes; otherwise continue within scope |
| Result | Opens concise result; performs visual UAT only if still required | Present candidate, exact diff, named checks, missing observations | A visual screenshot establishes appearance only; it cannot establish amount persistence |
| Finish | Accepts/applies if policy requires | Use Architecture §7's qualified integrator with proven exclusion, or owner-controlled application | Hash checking alone is insufficient; drift blocks automatic application and preserves the candidate/evidence |

An ordinary request to change the mobile preset implies a working control: displayed amount and intended value binding are part of the default contract. A source-only criterion is appropriate only for an explicitly source-level request. Full transaction persistence need not be added unless the change implicates it or the owner requested it. The contract must neither weaken the intent nor expand it into unrelated proof.

## 5. Escalation conditions

Escalate reasoning to DEEP DIVE when evidence contradicts the initial model, impact crosses a previously unknown domain boundary, the bug cannot be reproduced within the probe allowance, the fix requires a new architectural choice, or repeated failed repairs show the model is guessing.

Escalation does not restart the work or discard evidence. Same work identity, linked contract revisions, durable hypotheses and existing valid checks continue. Automatic effort/model escalation is permitted only inside an explicit provider/resource/capability grant. New financial allowance, production access or broader write scope requires a concrete owner decision. Production database writes remain prohibited regardless of mode.

Pause rather than escalate models when the missing input is an external observation, unknown effect, unavailable provider or exhausted resource bound. Premium reasoning does not solve absent permission or absent data.

## 6. What “fast” must mean

Proposed targets: no paid warm-up call; no mandatory five-phase traversal; no cold restart merely to change the UI activity label; cached deterministic baselines when valid; one bounded writer; no reviewer unless its independence improves the proof. The exact-edit happy path should usually need one engineering conversation and deterministic completion packaging, not two ceremonial reasoning roles.

Measure end-to-end latency including environment preparation and checks, not just model time. A fully isolated environment may dominate a tiny edit; maintain a trusted warm runner with resettable candidates if measurements justify it. Verify process termination, filesystem reset, cleared secrets and no cross-run state before reuse. Never skip containment to win a stopwatch comparison.

A pilot succeeds when comparable small tasks require fewer owner minutes without weaker evidence. Set numerical latency/cost targets after the first comparable observations; the historical $0.20 INSTANT criterion is not a valid forecast for a different architecture/provider.
