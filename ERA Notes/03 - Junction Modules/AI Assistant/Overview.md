## Key Concepts

- Rate limiting: 5/min per user, 10/min global
- Token tracking in `ai_messages` table
- Context injection from Transactions + Items
- Focus page AI briefing: cached 24h, max 2 manual refreshes/day
- **ERA turn latency and voice start (2026-09-02, HUB-36):** established `/era` threads now render user/assistant rows optimistically while a per-conversation queue preserves database order in the background; reply display and speech no longer wait for either message insert. Budget context's eight post-account reads, Schedule context's item/tag reads, and Ask AI's quota/rate-limit reads run concurrently. Usage logging runs with Next `after()` once the response is ready. Typed replies use the Azure PCM sentence queue (`useEraReplyTTS`) instead of waiting for a complete `/api/tts` MP3, with browser speech synthesis as fallback. `safeFetch` now distinguishes slow endpoints from real connectivity loss: timeouts trigger a health probe and never mark Offline or enter the mutation queue by themselves.
- **ERA intent routing — graceful `clarify` fallback** (2026-08-22, HUB-1): the ERA command-bar router (`src/features/era/intents/`) parses an utterance to a discriminated `Intent`. When it cannot confidently tell what was meant it now returns a dedicated `clarify` outcome (`reason: "ambiguous"` = more than one face matched; `reason: "weak"` = a single incidental keyword too soft to act on) instead of firing a wrong action. `clarify` carries no `face`, so `CommandBar` treats it exactly like `unknown` — **no face switch, no budget/transaction draft** — while still surfacing a clarifying prompt to the user. Concretely: non-spend text such as `spent 2 hours studying` produces no money draft, a weak money word no longer confidently switches faces, and a multi-face utterance asks the user to clarify rather than letting fixed face order silently decide. Behavior is locked by a table-driven fixture (`intents/rootIntentRouter.test.ts`, 39 cases). *(Note: the deterministic ERA keyword router is separate from `voice-conversation/intentClassifier.ts`, which is owned by HUB-2.)* *(Corrected 2026-08-22, same day: the original HUB-1 landing made cross-face fallback treat every non-null hit as equally confident, so a fully slot-filled match (e.g. schedule's `draftReminder` from "remind me…") could tie with another face's bare generic-keyword `switchFace` echo and wrongly resolve to `clarify/ambiguous` — "remind me to buy dinner ingredients" is the caught case. It also let the active face's own weak `clarify` short-circuit before cross-face routers ran at all, swallowing "remind me to buy groceries" (active=budget) before schedule ever saw it. Fixed same-session by tiering cross-face hits — `switchFace` is weak, everything else is strong — and by having the active face's `clarify` step aside for a stronger cross-face hit instead of winning outright. One row corrected, one row added to the fixture.)*
- **ERA intent resolution — `resolveIntent` is the single owner of every intent's side effect *and* its reply** (2026-08-22, HUB-12). `src/features/era/intents/resolveIntent.ts` dispatches an `Intent` to a per-face resolver in `intents/resolvers/`, which performs the real write and returns `{ text, metadata }`; `intents/formatters/` owns the wording. Three points matter when adding an intent here:
  - **Never let an intent fall through to `replyFormatter`.** `formatReply` is a *fallback for callers that format without resolving* — before HUB-12, `draftReminder` and `showAnalytics` reached the dispatcher, hit the `default` branch, and returned "Coming soon" while writing nothing. That is the worst failure shape available: the user reads it as success. If you add an `Intent` member, add its `case` in the same commit.
  - **Side effects that need React live behind `ResolveDeps`, not behind a branch in the caller.** `draftTransaction` needs the user's accounts, categories, the React Query client, and the Undo toast — all of which live in `useEraBudgetSubmit`. `CommandBar` injects that hook's `submit` as `ResolveDeps.submitBudgetDraft` rather than doing the write itself, so the write and the reply cannot disagree. It used to run on a parallel path in `CommandBar`, which is exactly how a failed draft came back as "Drafting $25.00…". `CommandBar` reads the draft id back out of `metadata.draftId`.
  - **`draftReminder` omits `due_at` when the parser found no date.** `resolvers/schedule.ts` runs `parseSmartText`, uses its cleaned `title` (not the raw utterance), and converts `dueDate`/`dueTime` with `localToISO` — but only when `confidence.date > 0`. Inventing a due time would fire an alert immediately. When a date was parsed with no time it defaults to noon, matching `MobileReminderForm`.
  Locked by `intents/resolveIntent.test.ts` (14 cases), which asserts the request body and the reply together.
- **ERA's voice is pooled, not scripted** (2026-08-22, HUB-15). `src/lib/era/phrasing.ts` supplies the mechanics — `pick` / `fill` / `say`, `describeWhen`, `money`, `plural`, `listOut`, `errorReply`, and a time-aware `greeting` — and every situation across all four faces owns a **pool** of slot-templated sentences chosen at random, so the same request twice does not return the same string. It sits in `src/lib/` because ERA and voice-conversation are separate standalone feature dirs. Four rules govern the pools, and breaking any of them is a bug, not a style choice:
  1. **Every variant carries the same facts.** Variation lives in the connective tissue; a variant that drops the amount or the due time makes the assistant lie some fraction of the time, with no way to tell which fraction. `intents/resolveIntent.test.ts` enforces this by driving `Math.random` across its range, collecting every sentence a pool can emit, and asserting the payload survives in all of them.
  2. **Slots, not concatenation** — `{name}` placeholders let a variant put the fact where its sentence wants it, which is most of what makes a set read as human. `fill` handles the spacing edge cases (flush against an opening quote vs. flush against a word) and cleans up separators stranded by an empty slot.
  3. **No jokes or personality-of-the-day.** Variants differ in rhythm and register only.
  4. **Never randomize an error's meaning.** `errorReply(diagnosis)` varies the apology and the retry nudge around a fixed diagnosis.
  *(Not yet applied to `src/features/voice-conversation/speechTemplates.ts`, which — as of HUB-17 below — is a `/chat`-only surface; HUB-16 tracks the remaining `/chat` divergence.)*
- **ERA Hub (`/era`) — one brain for typed and voice** (2026-08-25, HUB-17). Voice on `/era` had **zero working handlers**: `EraShell` mounted `useConversationMode` with only `onWillSpeak` wired, so `conversationEngine.executeNativeIntent` called `handlers.onLogExpense?.()` etc. through optional chaining, found nothing, and then **unconditionally spoke `successTemplate(intent)` anyway** — "Added $25 to Fuel" while writing nothing. This was strictly worse than HUB-16 (which is about `/chat`'s reminder handler specifically): every native voice intent on the Hub's own page was a false positive. Fixed by giving `ConversationHandlers` an optional `runTurn?: (text) => Promise<{reply, kind}>` capability (`conversationEngine.ts`) that, when present, replaces the five legacy callbacks entirely for that engine instance; `EraShell` wires it to the **same** `useEraTurn()` hook (`src/features/era/useEraTurn.ts`) that `CommandBar` calls for typed input — one classify (`rootIntentRouter.parse`) → one resolve (`resolveIntent`) → one persist (`era_messages`) path, so voice and typed can no longer disagree on a reminder's due time or whether a draft actually saved. The legacy five-callback path (`onLogExpense`/`onSetReminder`/…) is untouched and still serves `/chat`/`HubPage.tsx` — it also got the same false-success fix (only speaks `successTemplate` when a handler was actually present and ran), but its `classifyIntent`/`speechTemplates.ts` parsing stays separate from ERA's router, which is exactly what HUB-16 is still open to close. The Hub's single-string reply display (`EraReplyTranscript`) was replaced with `EraThreadTranscript`, a scrollable multi-turn view reading the same `era_messages` — the request "not only a single response, but a full conversation thread." Six confirmed-dead components deleted (`FaceCanvas`, `EraHubView`, `QuickFaceChips`, `EraFaceCard`, `FacePlaceholder`, `FaceHeader`, plus the superseded `EraTranscript`); dead `useEraStore.turns`/`pushTurn`/`clearTurns`/`eraActions` removed (zero importers, verified by grep). `pnpm test` green (1861), typecheck clean, no new deps. Verified end-to-end against the live dev DB: a real reminder ("remind me to call the bank tomorrow at 4pm") saved with the correct `due_at`, and `monthSpend`/`todaySchedule` queries returned correct data through the unified path — then deleted via the app's own delete endpoint (Hard Rule 26 — no direct DB writes).
- **ERA conversation surface — Report, New chat, History** (2026-10-03, owner-commissioned; HUB-85, HUB-86, HUB-52). The 240 px monospace strip above the command bar became a real thread (`src/components/era/EraConversation.tsx`, decisions in the pure `src/features/era/thread.ts`):
  - **Reading.** The person's messages are bubbles in their own color (Hard Rule #14); ERA's replies are plain 15–16 px text beside a small orb in the hue of the face that answered; time breaks after 30 min or a new day; ERA "thinking" dots for the whole turn (typed, voice or chip — `useEraStore.turnInFlight`); the confirm card, question chips and Report card render as the thread's newest turn, so they no longer float over it; the newest reply types out once and never replays on load or resume. In hub view an open conversation moves the ERA DOT to its module-mode position (same spring) and the thread fills the space down to the bar; with no conversation the hub is unchanged.
  - **New chat** clears everything a conversation leaves behind — focus memory ("it"), an open question or confirm card, the miss Ask AI would retry, the last applied lexicon rule — and the next sentence opens a new conversation. Once a chat has been silent for 30 minutes (the focus-memory TTL, i.e. when "it" stops resolving), a "New chat" divider closes the thread and the toolbar icon shows a dot; nothing is forced. A fresh chat's first sentence names its conversation client-side (`ensure_conversation` on the first write), so the first turn renders optimistically instead of waiting a round trip.
  - **History** (left icon): chats with at least one sentence, titled deterministically from their first sentence, grouped Today / Yesterday / This week / Earlier; tap previews read-only; Continue resumes with a clean context; Archive hides (Undo). Retention: every chat stays in `era_messages`; History lists the 50 most recent; a chat auto-closes after 6 h of silence.
  - **Report.** Under a reply that missed (router miss with no AI follow-up, failed/uncertain outcome, or an Ask AI prose answer to a missed request) ERA offers a quiet "Report" chip; any reply's details (tap) also offer it. The card asks Missed / Wrong plus an optional "Expected…" note. `POST /api/era/issues` snapshots the turns up to that reply with each turn's outcome and the ERA actions logged in that window (`src/lib/era/issueReport.ts`) into a system `era_messages` row (`intent_kind: "issue_report"`); the thread shows a "Reported" marker; Undo deletes only that row. The PM bridge imports reports (read-only toward the DB) into Hub & ERA › Now as `**Kind:** bug` items with the transcript — see `scripts/pm/era-issues.mjs` (R72) — and the PM Sprints page lists them as Hotfixes / Defects on the current week.
  - **Fixed on the way:** `handoff_consumed` system rows had rendered in the transcript as "› handoff consumed" and reached Ask AI's history as user turns; the confirm card and chips sat on top of the transcript at the same position.
- **Artifact contract — "ERA using the app's functionality"** (2026-10-04, HUB-89 follow-up, owner rule): **every ERA write (create / update / delete) leaves an Artifact** the owner can open. Before this, `logEraAction.ts` mapped six intent kinds to six hard-coded `era_actions.entity_type` values, so anything newer (contacts, shopping, recurring cover, shopping groups) wrote data but never appeared in /era → Artifacts, and the Activity Log's ERA row "Open" went to `/era`. Now:
  - **Adapters return `artifacts`** (`EraArtifact { action, entity, id, title, ref? }`, built with `eraArtifact()` from `src/lib/era/artifacts.ts`). Every result type carries the field — `ResolveResult`, `SlotResult`, `AmendResult`, `EraCapabilityResult`, `NativeActionResult` — and every existing write path was retrofitted: reminder create/draft/reschedule/complete/delete/skip/postpone, draft create/edit, draft confirm, transfer, debt, recurring cover, meal assign, memory save, shopping add/rename/qty/move/remove, shopping group create, NFC reminder, contact add. Lexicon aliases/rules are ERA's own vocabulary, not app data, so they leave no artifact.
  - **One logger, no per-feature mapping:** `src/features/era/recordArtifacts.ts` posts whatever the result carried; `useEraTurn` and `useEraAskAI.confirmProposal` are its only callers and also store `artifacts` on the assistant `era_messages.intent_payload`.
  - **Browse, group, undo (2026-10-10, HUB-101):** the Artifacts view shows one local day at a time (`GET /api/era/actions?from=&to=` for a day, `?view=days` for the days that have rows; ‹ › and the calendar skip empty days), grouped by app module (`ERA_ARTIFACT_MODULES` — hue = the module's ERA hue). Each reversible row has a persistent **Undo / Redo**. State is **derived, not stored**: `POST /api/era/actions/status` reads the target row (live / trashed / changed / gone), so a toast Undo, the Recycle Bin or another phone can never leave a stale button, and no migration exists. The action reuses the app's own routes — `DELETE /api/{items,catalogue/items,transfers,drafts}/[id]` (soft-delete + balance reversal) and `POST /api/recycle-bin/restore` (un-delete + balance re-apply). Only created/deleted verbs of bin-backed entities qualify (`eraArtifactReversal`: reminder, event, contact, place, draft, transfer); updates, debts (hard delete), memories, meal plans and shopping get no button until they have a real inverse (HUB-102). Offline taps fail rather than queue — never queue a money reversal.
  - **One link registry:** `ERA_ARTIFACT_ENTITIES` (label + `href(id, action, ref)`) is the only place a deep link is built — from entity + validated id/ref, never from captured text. `POST /api/era/actions` computes `route` server-side; the Activity Log API (`withEraLinks`) rebuilds the ERA row's link from the message's stored artifacts. Deleted → `/recycle-bin`.
  - **Generic adapter template:** `intents/resolvers/routeWrite.ts` (route → id → artifact → Undo via the route's inverse → one-line reply). New wirings use it; `/era-wire` mandates it.
  - **Enforced by** `src/features/era/artifacts.contract.test.ts` — one row per write path, red if an adapter forgets its artifact — plus `src/lib/era/artifacts.test.ts` (registry) and `src/features/activity-log/sourceHref.test.ts`.
  - **DB:** `migrations/2026-10-04_era-artifacts-any-entity.sql` replaces the fixed entity CHECK with a slug-shape check and adds `deleted`; until the owner runs it, artifacts of the new entities (contact, draft, shopping_*, recurring_payment) and any `deleted` row are rejected by the DB (500, logged server-side) and simply don't appear.
  - **Deep links:** contact → `/catalogue?item=<id>` (new `initialItemId` on `WebCatalogue`); reminder → `/reminders?openId=…&date=`; confirmed transaction → `/dashboard?openId=`. Transfer, debt, draft, meal plan, memory, recurring and shopping still open their module page — those modules have no per-item URL yet (Pain Inventory).
- **Learned references: Events + Places** (2026-10-04, HUB-94 / HUB-88). ERA creates events: "add an event …", "schedule a meeting …", "book an appointment …", "new event: …" and "add X to my calendar" become `draftEvent` (`intents/eventText.ts` → `resolvers/events.ts`).
  - **Flow:** the event is written first through `POST /api/items` (type `event`, Undo = DELETE). With no date, ERA asks **When?** [Today] [Tomorrow] and nothing is written yet. With no place, ERA asks **Where?** with chips for up to 3 saved places (pinned first) plus [Skip]. A new place is PATCHed onto the event, then ERA asks `Save "X" to Places?` [Save] [No]. A saved place or alias tag in the sentence fills the location silently and stores `metadata_json.place_id`. Repeating events hand off to the form. "Add X as a location" (`addPlace`) saves directly.
  - **Places storage:** Catalogue items in a custom module ERA creates on first save, marked `settings_json.era_role = "places"` (`POST /api/catalogue/modules` now accepts `settings_json`). An existing module named Places/Locations is adopted instead. Aliases are the item's **tags**. There is no DB change, and items are private by default, like contacts.
  - **Gotchas:** the id travels as `metadata.eventId`, never `itemId`, because focus memory and rehydration read `itemId` as a reminder and "move it to 9" would PATCH a non-existent `due_at`. "When?" and "Where?" take free text, so `intents/freeTextAnswer.ts#isNewRequest` routes a real command typed instead ("add milk to the list") as a new request. Implicit page doors don't count, because "gym" is a valid place. `PATCH /api/items/[id]` only writes `event_details.location_text` when `start_at`/`end_at` ride along, so the place PATCH resends them. parseSmartText's title isn't used for events, because its category pass eats words like "parents" or "dentist". Only its date/time (`parseRelativeDate`, `parseTime`, now exported) are used, and a time found only inside a word ("Jacob" → "cob") is ignored.
- **Budget AI analysis** (2026-06-27): analysis-intent messages return a strict `AnalysisReport` JSON (Gemini `responseSchema` + Zod + deterministic fallback) that renders as a markdown chat answer and, via **View as Dashboard**, as recharts widgets. The report JSON is persisted on the assistant `ai_messages` row (`analysis_report`) so historical answers can reopen the dashboard without another AI call. See [[Spending Analysis Report]].
