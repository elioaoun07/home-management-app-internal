## P0 action trust — 2026-10-11 (SCH-24 / HUB-109)

**Implemented in the repository; SQL application, current RLS evidence and mobile/device acceptance are pending.** This continues the Phase 5 roadmap through the existing registry, executor, journal and source APIs. It adds no agent framework, capability family, autonomous retries or cross-module transaction engine.

### Source completion

The defect lived in Schedule as well as ERA: `POST /api/items` returned 201 after child failures, while the three browser create hooks implemented another sequence of parent/child writes. The prerequisite route could insert a trigger without making its item dormant. A parent artifact alone proved neither the alert nor the trigger existed.

`src/lib/items/createContract.ts` validates the complete request before dispatch and prepares the same payload for forms, ERA and offline replay. `create_item_complete` saves the parent, typed details, subtasks, alerts, recurrence and prerequisites in one authenticated, SECURITY INVOKER transaction. The receipt includes `completion.status = complete` and child IDs. Add/remove-prerequisite RPCs lock the owned item and commit the trigger change with its dormant/pending transition. Existing RLS stays authoritative; explicit owner/active-household/tag-state checks add no policy widening. NFC creation now sends its prerequisite in the original item POST.

A returned PostgreSQL rejection proves rollback; a missing RPC proves dispatch did not start. A lost response, transport error or incomplete receipt is **unknown**, not rollback or success. ERA retains any acknowledged legacy parent artifact, refreshes source queries and says to check Schedule. Precision create hooks require the same receipt and refresh on failure too. Offline item creates durably set `reviewRequired` before dispatch; unknown attempts retain their input and cannot replay, expire or disappear through create/delete cancellation. Successful receipt handling keeps that fence until queue removal. IndexedDB transaction completion, not only request success or memory fallback, is required to dispatch safely. This prevents blind repeats; it does **not** establish source idempotency or an automatic reconciliation service (HUB-46).

Drafts save without alerts. Draft-plus-trigger requests are rejected before writing, rather than silently converting an unconfirmed draft to an activatable dormant item. Recurrence still uses the existing RRule helper; no new expansion path was added. The migration permits zero-day alert offsets, matching the picker's same-day custom clock time. Recurring custom-time alerts are rejected before saving: the current cron advances numeric offsets and cannot preserve that wall-clock rule. SCH-7/SCH-9 retain broader recurrence/notification lifecycle work. Google Calendar backup remains best effort and outside the local completion guarantee.

### Effective consent

Every registered write has a reviewed confirmation contract: an action title and compact effective fields, derived from validated slots, the existing parser/defaults and live source lookups. `EraActionPreview` is shared by transient and saved cards. Model prose and step labels cannot describe the action the user approves. The original request remains available for comparison. Reminder previews show the real title, anchored date/time, priority, one-time effect and due-time push; draft confirmation shows the selected amount/currency/account/date; meal assignment shows the actual unique recipe/date/default lunch and occupied-slot replacement; shopping shows actual ingredients, list and group. Deletion explicitly says Recycle Bin.

Dependencies stay visibly pending until their read completes. Adapters compare the displayed consent snapshot with effective values immediately before dispatch and recheck the request boundary after reads. New/changed values return `awaiting_confirm` instead of writing. Confirm continues from acknowledged receipts, skipping completed reads/writes. The journal persists that snapshot, resets consent and restores the card after reload; Resume never grants new consent. Registered writes without a confirmation contract fail admission. Meal lookup no longer uses `limit=1` to conceal ambiguity.

Known rollback/failure, known partial goals and unknown writes have distinct outcomes. Earlier artifacts remain inspectable. Native money/occurrence/group workflows retain their existing lifecycle; their card titles are deterministic, but full saved-consent/native convergence and source revision preconditions remain HUB-46. A deterministic preview proves what the admitted adapter will attempt, not semantic equivalence to every natural-language constraint or a revision lock across another client's concurrent edits. HUB-105 still owns whole-goal interpretation/evaluation.

## Final review and hardening — 2026-10-11 (HUB-108)

**Verdict: a useful supervised assistant and a sound integration foundation; not yet a dependable general operator of the whole application.** ERA can compose reviewed primitives into requests that have no dedicated workflow implementation. It cannot reliably establish that every part of an arbitrary request is achievable, prove that its proposed plan preserves every constraint, or repair an unknown write autonomously. Passing adapter tests establishes execution contracts, not general intelligence or daily production readiness.

This review covers the working tree after HUB-103–106, repository history through `82a564f0`, the accepted Top Layer decisions, actual route/adapter/hook code and prior Gym evidence. Initial phases were already uncommitted; this review is not evidence that their deployment occurred. The dated receipts below supersede older aggregate test counts, not the original product constraints. No production database, paid model or speech API was called during this review.

### Challenge against the vision

| Dimension | Evidence-backed assessment and remaining limit |
|---|---|
| Intelligence / language | A deterministic native router plus a model on explicit compound requests, dialogue gaps and manual Ask AI can handle paraphrases and contextual follow-ups. Native routing still uses grammar/heuristics and can consume an incomplete interpretation. Plans are checked for schema and safety, not for semantic equivalence to the whole request. Unsupported constraints can still be omitted by a model while leaving a valid plan. Prose-only answers have no factual execution guarantee. |
| Capability discovery | One executable registry produces the model catalog; static inventory exposes integration candidates. This is useful application knowledge, but the full application is not executable. An adapter must explicitly define permission, identity, effect, output and failure semantics before adoption. |
| Multi-step work | Up to six sequential steps can bind real earlier outputs; every receiving slot is preflighted before later writes. This generalizes combinations of those primitives. There are no result-driven branches, loops, autonomous replanning, pantry subtraction, recipe scaling or multi-module atomic transactions. A partial plan is not a completed user goal. |
| Adaptive memory | Bounded owner-attributed history, explicit lexicon/preferences, acknowledged experience and source coverage inform the model across faces. Retrieval is lexical: at most 30 days/400 rows/six episodes plus a 24-turn tail. It is not whole-history semantic recall, model training or reliable automatic habit learning. Historical statements are not current source facts; they grant no target identity or consent. Shared Brain notes remain a separate readiness gap. |
| Autonomy | Reads can run immediately; confirmed writes reuse app operations. Native low-risk actions follow their existing policy. | Reliability / recovery | Default in-memory execution now uses the same admission, live-target and artifact checks for single actions and plans. ### Hardening implemented in this review

1. **Bind model cards to the original owner, conversation, time and time zone.** Recheck at confirmation and between steps even when the journal is disabled. A late model response cannot attach to another account. New chat suspends subsequent dispatch; an already acknowledged effect keeps its artifact. Relative dates use the request's original anchor.
2. **Run single registered actions through `executePlan`.** Single cards now get live reminder revalidation, focus expiry, missing-artifact uncertainty, shared cache refresh and structured outcome receipts. A double tap still consumes only one card.
3. **Refuse invalid actions truthfully.** Rejected single/NFC proposals return “I couldn't validate that action. Nothing was changed.” They no longer repeat model-authored claims such as “Moved” when no adapter ran.
4. **Keep NFC partial facts.** Record the created reminder even if trigger setup fails, invalidate Schedule and label the trigger unverified. Do not offer a blind retry or claim the compound action succeeded.
5. **Do not silently drop recurrence.** A recurrence recognized by the existing parser is handed to Schedule without dispatch, including an answer to a pending reminder question. The capability catalog explicitly limits creation to one-time reminders. This does not prove the parser recognizes every recurring phrase; SCH-7 remains broader.
6. **Apply strict money speech-act admission.** Conditional draft confirmations such as “Confirm the latest draft if my salary lands” cannot become immediate model-plan writes.
7. **Meter actual model responses and fail closed on quota-read errors.** Input includes the real system/catalog/context; output includes reasoning/structured response, even when admission rejects it. Missing metadata is explicitly estimated; absent provider responses are marked `unknown:no-response`. This closes a concrete Ask AI undercount, not all of HUB-44.

No business-rule engine, UI redesign, new model call, new capability family or migration was added. Regression tests exercise the actual React hook/store/executor boundary with isolated dependencies, the real reminder parser/resolver, SDK response parsing and the actual API handler. They are not browser or production tests.

## ERA Agent v1 — 2026-10-10 (HUB-103 / HUB-100)

The initial agent extends the existing ERA pipeline: typed and spoken sentences enter `useEraTurn`; explicit compound requests and recipe-to-shopping dependencies reach `/api/era/ask` before a single-action parser can consume half the request. Native single-action commands keep their existing path. Language-gap misses retain capped automatic escalation, and Ask AI remains available manually. A compound request starts a fresh request instead of answering an old date/group question.

Gemini discovers available actions from the same capability registry used for validation and execution. The catalog now contains 17 capabilities, adding `shopping.add`, `shopping.list`, `recipe.ingredients` and `reminder.find`. A `propose_plan` contains at most six ordered steps. Slots bind to declared earlier outputs with `{step, field}`; the model cannot invent IDs, endpoints or executable code. Admission validates the entire plan, literal slots, dependency ordering/type compatibility and entity domain before any step runs. Execution validates real output data again. Named reminders resolve uniquely among owned, non-recurring open reminders. A pronoun remains bound to its original focus ID and must still be current/unexpired at confirmation.

Read-only plans and single registered reads run immediately and display application results. Plans containing writes show the existing Confirm/Dismiss card with deterministic effective fields (HUB-109). A shared synchronous store lock prevents typed, voice and multiple mounted cards from dispatching the same confirmation twice. Every write uses the existing resolver and application routes, `safeFetch`, date parser and permissions; there is no new database schema, balance calculation, recurrence engine, offline queue or independent assistant.

## Durable execution foundation — 2026-10-10 (HUB-104)

Phase 2's in-memory lock and transcript receipts were sufficient for one live invocation, but could not arbitrate two clients, restore pending consent after reload, preserve dependency outputs independently of message persistence, or distinguish a failed dispatch from an unknown result. Persisting the entire Zustand store or replaying the transcript would preserve stale controls and still lack a write claim. A new offline queue or background agent would duplicate existing infrastructure without closing the source transaction gap.

The foundation therefore adds one owner-bound `era_runs` aggregate per registered agent plan, while retaining `executePlan`, source resolvers, existing permissions and query keys. Ask AI single registered proposals become one-step plans. The plan, original request/date/time zone/focus, confirmation, ordered step state, validated outputs, artifacts and serializable pending question are journaled independently of optional transcript delivery. Execution remains sequential and limited to six registered steps. No new model calls, worker, recurrence engine, financial logic or offline queue are introduced.

### Execution and recovery contract

| State | Behavior |
|---|---|
| Awaiting confirmation | Saved consent card; no domain dispatch before Confirm. |
| Ready | Explicit Resume uses acknowledged outputs and skips completed steps. |
| In progress | Persisted attempt UUID and version claim precede source dispatch. |
| Waiting | The exact step owns its date/group question or serializable shopping-group confirmation. Answering completes that step; Resume continues the remainder. |
| Stopped | Validation or a known refusal prevented dispatch; reads can be retried. |
| Check app | A write outcome is unknown, including a recovered interrupted write, missing artifact or partial batch. Inspect linked artifacts/source data, then Skip or Stop; no replay button. |
| Done / Partial / Stopped | Terminal receipts remain inspectable. Skipped work is Partial, never reported as all done. |

`save_era_run` uses the authenticated owner's identity, conversation ownership and compare-and-swap version in one PostgreSQL transaction. Each transition wins once. Attempt IDs fence late completions after recovery. A running attempt can be recovered after two minutes without progress: reads become Ready; writes become Check app. Shopping checkpoints each acknowledged create before the next POST and refreshes the timeout at each checkpoint. Losing the checkpoint stops the batch and group follow-up. Failed journal creation never falls back to an unjournaled write.

Receipts and the `era_actions` projection commit together. Action IDs are deterministic per run/step/entity/id/verb, so re-projecting earlier receipts does not duplicate the artifact log. Canonical deep links still come from `src/lib/era/artifacts.ts`. Source cache invalidation also occurs when a checkpoint fails after a source write. Transcript inserts are still best-effort; their loss does not remove saved progress. Pending continuations are validated data, never closures or executable instructions.

New chat or selecting another conversation suspends later steps at the next boundary. An already-dispatched write can finish and save its receipt to the original run; it does not attach the old answer or focus to the new chat. History → Continue restores the original conversation's cards. Owner-scoped query keys and server checks isolate saved runs from a partner/account switch. The list fetches the oldest 100 unfinished runs plus the latest terminal receipt; completed traffic cannot hide that recovery window. Closing the browser stops client execution; no work resumes automatically on reload or another device.

Relative dates are parsed against the original request date, so a later Resume cannot turn “tomorrow” into a different day. Resume refuses a changed device time zone. Unfinished pronoun targets keep the existing focus expiry; completed focus steps do not invalidate unrelated remaining steps. Named reminder targets are checked again through the source Schedule bundle and must still be owned, open and non-recurring before a resumed write. Missing dependency outputs, changed capability admission or unsupported snapshot versions stop execution rather than guessing.

### Deliberate limits

- A journal claim prevents competing dispatches **within a saved run**; it is not source-endpoint exactly-once execution. A source commit followed by a lost response/checkpoint remains ambiguous. A fresh request can still duplicate existing source data. **HUB-46** remains open for endpoint idempotency and verified owner-bound reconciliation.
- Native deterministic single-command capture, standalone native proposal cards, and the existing NFC reminder/prerequisite two-write path are not converted to durable runs. Their existing behavior is preserved; do not describe all ERA writes as recoverable yet.
- Partial batch recovery retains acknowledged artifacts but does not automatically create the missing shopping items. Skip advances past that step; it neither undoes its artifacts nor supplies absent outputs to dependent steps. There is no whole-plan rollback. Existing artifact inverses remain under **HUB-102**.
- Consent is for the immutable saved plan, not an open-ended replanning loop. Source resolvers still revalidate inputs and permissions. Expired or changed requests can be stopped and restated; automatic compensation, background retries and plan editing are deliberately absent.

### Implemented context contract

`src/lib/ai/eraAdaptiveContextSource.ts` performs six independent, request-scoped reads using the authenticated server client: past private messages, the current private conversation, live lexicon, current own account names, personal month-start configuration, and `get_household_activity`. Message predicates constrain both message and parent conversation to the speaker and exclude archived parents. No service role, raw activity table, partner chat, clinical detail, source write or shared-memory scan is used. Each optional read has a two-second abort budget; errors/missing infrastructure mean **unavailable**, not an empty successful read. Existing face context remains available.

`eraAdaptiveContext.ts` assembles a bounded evidence packet on every face. It searches the latest 400 historical rows within 30 days, excludes the current conversation, ranks user utterances using document-frequency-weighted term overlap, and retains up to four topical episodes plus two recent experiences. This is lexical retrieval with model interpretation, not embeddings, semantic search or model retraining. User statements remain attributed and dated; assistant prose is never promoted to a fact. Action episodes require acknowledged outcomes; writes need actual artifact receipts, and plans need every declared step. Failed, pending, uncertain, partial, handed-off and reported wrong interactions are excluded from successful experience. Reports and miss classifications instead feed a small gap summary.

Lexicon references are rebound to current **own** account names; revoked, missing, partner and unsupported group references are omitted. Explicit choices retain their conditions. An example requires a linked acknowledged source before it can be included as tentative observation; unlinked legacy chip choices are excluded. No observation becomes an automatic default. Activity contributes only module counts for currently available rows both owned and acted on by the speaker, never titles, values, source IDs or partner activity. Counts describe a bounded event sample, not how often the household uses every feature.

The packet is capped at 12,000 characters. Each source declares `available`, `sampled` or `unavailable`. Ask AI's existing model receives the packet as historical data: current instructions override past choices; conflicts require clarification; old entities require a fresh registered lookup; historical IDs never supply FOCUS or confirmation. Registered plan validation, source permission checks, artifacts and Confirm remain authoritative. Retrieval neither adds executable tools nor changes money/recurrence logic.

Conversation continuity now merges up to 32 saved rows with an owner-bound optimistic tail, removes system bookkeeping and the current question before overlap detection, and supplies at most 24 turns/12,000 characters. Optimistic rows carry the capture session's user ID, and confirmation by the server binds locally seeded conversations to their real owner. Ask AI authenticates before consuming cached chat, uses the live QueryClient page rather than a stale render closure, rejects a foreign conversation, and excludes anonymous/foreign cached rows. A miss during recent active dialogue can reach the existing capped model path without repeating a domain keyword; negated writes still never auto-escalate. New chat and the existing 30-minute idle boundary do not inherit this exception.

Assistant rows persist a `contextReceipt` containing source coverage, selected message/rule IDs and packet size, without copying the private packet into the transcript. Input estimates include the added packet; complete prompt/model usage accounting remains HUB-44. There is no new cache, database table, offline queue, worker or migration. Optional context failures degrade to current dialogue and existing capabilities; offline AI behavior remains the existing `safeFetch` behavior.

### Decisions, evidence and next evolution

Keep working context, episodic evidence, explicit preferences and source-owned facts distinct. Request-time evidence reuse gives immediate value without another memory store that can drift from deletions, privacy changes or corrections. Permanent preference extraction would require attribution, correction/revocation, conflict/version rules, personal versus household scope and an explicit promotion policy; silently writing every inferred trait to Brain would violate its current shared audience. Repeated activity also cannot authorize a write or overcome an unsupported capability.

The next priorities are source-owned read adapters under HUB-69/71/81, resolution of personal/shared note scope under D17/HUB-70, then measured longer-horizon retrieval. Retain a full capability index; use the gap summary and Reports to distinguish parser misses, missing adapters and source-data/readiness problems. An agent can surface a gap and route it to existing Report/precision tools; it cannot code or grant itself a missing capability. Broader retrieval should be admitted against source freshness/privacy and paraphrase recall benchmarks before adding embeddings or another persistent store. Source idempotency (HUB-46), inverse coverage (HUB-102) and token attribution (HUB-44) remain independent prerequisites for wider action autonomy.

- **ERA turn latency and voice start (2026-09-02, HUB-36):** established `/era` threads now render user/assistant rows optimistically while a per-conversation queue preserves database order in the background; reply display and speech no longer wait for either message insert. Budget context's eight post-account reads, Schedule context's item/tag reads, and Ask AI's quota/rate-limit reads run concurrently. Usage logging runs with Next `after()` once the response is ready. Typed replies use the Azure PCM sentence queue (`useEraReplyTTS`) instead of waiting for a complete `/api/tts` MP3, with browser speech synthesis as fallback. `safeFetch` now distinguishes slow endpoints from real connectivity loss: timeouts trigger a health probe and never mark Offline or enter the mutation queue by themselves.
- **ERA intent routing — graceful `clarify` fallback** (2026-08-22, HUB-1): the ERA command-bar router (`src/features/era/intents/`) parses an utterance to a discriminated `Intent`. When it cannot confidently tell what was meant it now returns a dedicated `clarify` outcome (`reason: "ambiguous"` = more than one face matched; `reason: "weak"` = a single incidental keyword too soft to act on) instead of firing a wrong action. `clarify` carries no `face`, so `CommandBar` treats it exactly like `unknown` — **no face switch, no budget/transaction draft** — while still surfacing a clarifying prompt to the user. Concretely: non-spend text such as `spent 2 hours studying` produces no money draft, a weak money word no longer confidently switches faces, and a multi-face utterance asks the user to clarify rather than letting fixed face order silently decide. Behavior is locked by a table-driven fixture (`intents/rootIntentRouter.test.ts`, 39 cases). *(Note: the deterministic ERA keyword router is separate from `voice-conversation/intentClassifier.ts`, which is owned by HUB-2.)* *(Corrected 2026-08-22, same day: the original HUB-1 landing made cross-face fallback treat every non-null hit as equally confident, so a fully slot-filled match (e.g. schedule's `draftReminder` from "remind me…") could tie with another face's bare generic-keyword `switchFace` echo and wrongly resolve to `clarify/ambiguous` — "remind me to buy dinner ingredients" is the caught case. It also let the active face's own weak `clarify` short-circuit before cross-face routers ran at all, swallowing "remind me to buy groceries" (active=budget) before schedule ever saw it. Fixed same-session by tiering cross-face hits — `switchFace` is weak, everything else is strong — and by having the active face's `clarify` step aside for a stronger cross-face hit instead of winning outright. One row corrected, one row added to the fixture.)*
- **ERA intent resolution — `resolveIntent` is the single owner of every intent's side effect *and* its reply** (2026-08-22, HUB-12). `src/features/era/intents/resolveIntent.ts` dispatches an `Intent` to a per-face resolver in `intents/resolvers/`, which performs the real write and returns `{ text, metadata }`; `intents/formatters/` owns the wording. Three points matter when adding an intent here:
  - **Never let an intent fall through to `replyFormatter`.** `formatReply` is a *fallback for callers that format without resolving* — before HUB-12, `draftReminder` and `showAnalytics` reached the dispatcher, hit the `default` branch, and returned "Coming soon" while writing nothing. That is the worst failure shape available: the user reads it as success. If you add an `Intent` member, add its `case` in the same commit.
  - **Side effects that need React live behind `ResolveDeps`, not behind a branch in the caller.** `draftTransaction` needs the user's accounts, categories, the React Query client, and the Undo toast — all of which live in `useEraBudgetSubmit`. `CommandBar` injects that hook's `submit` as `ResolveDeps.submitBudgetDraft` rather than doing the write itself, so the write and the reply cannot disagree. It used to run on a parallel path in `CommandBar`, which is exactly how a failed draft came back as "Drafting $25.00…". `CommandBar` reads the draft id back out of `metadata.draftId`.
  - **`draftReminder` omits `due_at` when the parser found no date.** `resolvers/schedule.ts` runs `parseSmartText`, uses its cleaned `title` (not the raw utterance), and converts `dueDate`/`dueTime` with `localToISO` — but only when `confidence.date > 0`. Inventing a due time would fire an alert immediately. When a date was parsed with no time it defaults to noon, matching `MobileReminderForm`.
  Locked by `intents/resolveIntent.test.ts` (14 cases), which asserts the request body and the reply together.
- **ERA's voice is pooled, not scripted** (2026-08-22, HUB-15). `src/lib/era/phrasing.ts` supplies the mechanics — `pick` / `fill` / `say`, `describeWhen`, `money`, `plural`, `listOut`, `errorReply`, and a time-aware `greeting` — and every situation across all four faces owns a **pool** of slot-templated sentences chosen at random, so the same request twice does not return the same string. It sits in `src/lib/` because ERA and voice-conversation are separate standalone feature dirs. Four rules govern the pools, and breaking any of them is a bug, not a style choice:
  1. **Every variant carries the same facts.** Variation lives in the connective tissue; a variant that drops the amount or the due time makes the assistant lie some fraction of the time, with no way to tell which fraction. `intents/resolveIntent.test.ts` enforces this by driving `Math.random` across its range, collecting every sentence a pool can emit, and asserting the payload survives in all of them.
  2. **Slots, not concatenation** — `{name}` placeholders let a variant put the fact where its sentence wants it, which is most of what makes a set read as human. `fill` handles the spacing edge cases (flush against an opening quote vs. flush against a word) and cleans up separators stranded by an empty slot.
  3. **No jokes or personality-of-the-day.** Variants differ in rhythm and register only.
  4. **Never randomize an error's meaning.** `errorReply(diagnosis)` varies the apology and the retry nudge around a fixed diagnosis.
  *(Not yet applied to `src/features/voice-conversation/speechTemplates.ts`, which — as of HUB-17 below — is a `/chat`-only surface; HUB-16 tracks the remaining `/chat` divergence.)*

  - **One link registry:** `ERA_ARTIFACT_ENTITIES` (label + `href(id, action, ref)`) is the only place a deep link is built — from entity + validated id/ref, never from captured text. `POST /api/era/actions` computes `route` server-side; the Activity Log API (`withEraLinks`) rebuilds the ERA row's link from the message's stored artifacts. Deleted → `/recycle-bin`.
  - **Generic adapter template:** `intents/resolvers/routeWrite.ts` (route → id → artifact → Undo via the route's inverse → one-line reply). New wirings use it; `/era-wire` mandates it.
  - **Enforced by** `src/features/era/artifacts.contract.test.ts` — one row per write path, red if an adapter forgets its artifact — plus `src/lib/era/artifacts.test.ts` (registry) and `src/features/activity-log/sourceHref.test.ts`.
  - **DB:** `migrations/2026-10-04_era-artifacts-any-entity.sql` replaces the fixed entity CHECK with a slug-shape check and adds `deleted`; until the owner runs it, artifacts of the new entities (contact, draft, shopping_*, recurring_payment) and any `deleted` row are rejected by the DB (500, logged server-side) and simply don't appear.
  - **Deep links:** contact → `/catalogue?item=<id>` (new `initialItemId` on `WebCatalogue`); reminder → `/reminders?openId=…&date=`; confirmed transaction → `/dashboard?openId=`. Transfer, debt, draft, meal plan, memory, recurring and shopping still open their module page — those modules have no per-item URL yet (Pain Inventory).
- **Learned references: Events + Places** (2026-10-04, HUB-94 / HUB-88). ERA creates events: "add an event …", "schedule a meeting …", "book an appointment …", "new event: …" and "add X to my calendar" become `draftEvent` (`intents/eventText.ts` → `resolvers/events.ts`).
  - **Flow:** the event is written first through `POST /api/items` (type `event`, Undo = DELETE). With no date, ERA asks **When?** [Today] [Tomorrow] and nothing is written yet. With no place, ERA asks **Where?** with chips for up to 3 saved places (pinned first) plus [Skip]. A new place is PATCHed onto the event, then ERA asks `Save "X" to Places?` [Save] [No]. A saved place or alias tag in the sentence fills the location silently and stores `metadata_json.place_id`. Repeating events hand off to the form. "Add X as a location" (`addPlace`) saves directly.
  - **Places storage:** Catalogue items in a custom module ERA creates on first save, marked `settings_json.era_role = "places"` (`POST /api/catalogue/modules` now accepts `settings_json`). An existing module named Places/Locations is adopted instead. Aliases are the item's **tags**. There is no DB change, and items are private by default, like contacts.
  - **Gotchas:** the id travels as `metadata.eventId`, never `itemId`, because focus memory and rehydration read `itemId` as a reminder and "move it to 9" would PATCH a non-existent `due_at`. "When?" and "Where?" take free text, so `intents/freeTextAnswer.ts#isNewRequest` routes a real command typed instead ("add milk to the list") as a new request. Implicit page doors don't count, because "gym" is a valid place. `PATCH /api/items/[id]` only writes `event_details.location_text` when `start_at`/`end_at` ride along, so the place PATCH resends them. parseSmartText's title isn't used for events, because its category pass eats words like "parents" or "dentist". Only its date/time (`parseRelativeDate`, `parseTime`, now exported) are used, and a time found only inside a word ("Jacob" → "cob") is ignored.
