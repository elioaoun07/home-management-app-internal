## Candidate handover template

**Standing process requirement, recorded 2026-10-19 from the October 18 owner request.** For every delivered defect fix or new feature, the delivering agent supplies this completed handover before asking the owner to test or accept it. Keep it with the existing candidate/result artifacts or the item's existing UAT record, and link it from the owning Master Book handover. The dated Delivery trials below retain their historical results; they are not a substitute for scenarios for a newly delivered item.

**Identity:** item and acceptance-criteria links; run, candidate ID/generation/digest, Result/plan revision; tested build/environment and observation date. For direct delivery, name the exact source revision and changed-file hashes. State whether the candidate is available in that environment or still needs separately authorized application/deployment. Do not invite testing against an unchanged build.

**Prerequisites and data:** required role/account, device/browser, sign-in, setup and starting state; exact isolated records/values and reset/cleanup steps. Name any owner-only setup or permission and mark the scenario BLOCKED until it exists. A scenario is not authorization for production writes, paid calls, installation or Apply.

Repeat this block per scenario, replacing all placeholders:

> **Scenario ID / title / acceptance link:** `<item>-M1 / observable behavior / exact criterion`
>
> **Type:** defect reproduction / feature / regression / edge case
>
> **Start and navigation:** exact route and visible controls from a known starting state.
>
> **Data:** exact inputs and prerequisite records for this case.
>
> **Steps and expected results:** numbered actions, each with its expected visible value/state; include save/reload/reopen when relevant. For a defect, give the original reproduction and former symptom, then the corrected result on this candidate. Never ask the owner to reinstall a broken version merely to reproduce it.
>
> **Regression/edge coverage:** relevant adjacent behavior and boundary/negative/retry cases; explain any non-applicable case briefly.
>
> **Actual:** Pending / PASS / FAIL / BLOCKED; observation, tester, date, build/device and evidence link. Default is Pending.
>
> **Reset:** exact safe cleanup or restoration steps, or why none is needed.

**Untested limitations (separate section):** list each untested scenario/criterion/device/integration, why it is untested, the impact and the next evidence/action needed. Owner-only evidence stays Pending or BLOCKED; no invented PASS. A changed candidate requires a new bound handover and relevant retesting; earlier results remain historical.

**Automated verification (separate section):** command/criterion, actual result/counts, candidate/environment and receipt link. This supports the handover but never replaces manual instructions or establishes owner acceptance. Record handover completeness separately from implementation, automated verification, Apply/deployment and owner UAT.

**Runtime gap for separate approval:** current V2 prompts/results do not require these scenarios, and protected-check success can close a verified candidate without them. Reuse `interaction.mjs` and the existing worker output/import path to supply a bounded structured handover; validate and freeze it against candidate/acceptance identity in `journey.mjs` using `store.mjs` artifacts; expose its completeness/limitations through existing Result obligations and the shared artifact reader on desktop/phone.
